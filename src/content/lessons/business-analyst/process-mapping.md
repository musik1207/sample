## この範囲で問われること

- 業務プロセスを図にする目的と手法
- 現状（As-Is）と目指す姿（To-Be）
- 適切な詳細度（レベル）の選び方
- プロセスの改善点の見つけ方

## 1. なぜプロセスを図にするのか

- 関係者の**認識をそろえる**（同じ業務でも人によって理解が違う）
- **ムダ・手戻り・属人化**を見つける
- 要件やユーザーストーリーの**抜け漏れを防ぐ**

## 2. 図の種類

| 図 | 特徴 |
|---|---|
| **スイムレーン図** | 役割（部門・人・システム）ごとにレーンを分け、誰が何をするかを表す。最もよく使われる |
| **UPN（Universal Process Notation）** | Salesforce のエコシステムでよく使われる記法。「誰が・何を・どの資料で」を簡潔に書き、詳細な下位プロセスにドリルダウンできる |
| **BPMN** | 業務プロセスの標準記法。分岐やイベントを厳密に表せる |
| **フローチャート** | シンプルな手順や分岐を表す |
| **バリューストリームマップ** | 工程ごとの時間や待ちを可視化し、ムダを見つける |

## 3. As-Is と To-Be

1. **As-Is（現状）**: 今の業務をありのまま描く。理想ではなく**実際のやり方**を描くことが大切。
2. **課題の特定**: 手作業、二重入力、承認待ち、情報の行き違いなど。
3. **To-Be（あるべき姿）**: 課題を解決した将来の業務。Salesforce の標準機能でどう実現するかも考える。
4. **ギャップ分析**: As-Is と To-Be の差が、要件になる。

> **「現状の業務をそのままシステム化する」のは避ける**のが基本です。まず業務を見直し、Salesforce の標準機能に業務を合わせられないかを検討します。

## 4. 詳細度（レベル）

- **レベル 1**: 全体像（例: リード獲得 → 商談 → 受注 → 請求）
- **レベル 2〜3**: 各工程の詳しい手順
- 相手に合わせてレベルを変える: 経営層には全体像、開発者には詳細な手順。
- 1 枚の図に詰め込みすぎない。**ドリルダウン**で詳細に分ける。

## 5. 改善点の見つけ方

- **手作業の繰り返し** → 自動化（Flow）の候補
- **二重入力・転記** → 連携やデータの一元化
- **承認の待ち時間** → 承認プロセスの見直し・モバイル承認
- **情報を探す時間** → レポート・ダッシュボード・検索の改善
- **例外処理** → 本当に必要か、標準化できないかを確認
