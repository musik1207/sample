## この範囲で問われること

- Flow の種類と起動方法
- レコードトリガーフローの「保存前」と「保存後」
- 承認プロセス
- 要件に合った自動化ツールの選び方

> 2025 年末でワークフロールールとプロセスビルダーはサポート終了。新しい自動化は **Flow** で作るのが前提です。

## 1. Flow の種類

| 種類 | 起動方法 | 例 |
|---|---|---|
| **画面フロー** | ユーザーが操作（ボタン・ページ上のコンポーネント・アクション） | 入力ウィザード、申請画面 |
| **レコードトリガーフロー** | レコードの作成・更新・削除 | 商談が成立したら ToDo を作る |
| **スケジュールトリガーフロー** | 指定日時・頻度で一括実行 | 毎朝、期限切れのケースを更新 |
| **プラットフォームイベントトリガーフロー** | プラットフォームイベントの受信 | 外部システムからの通知で処理 |
| **自動起動フロー（トリガーなし）** | 他のフローや Apex、REST API から呼ばれる | 共通処理のサブフロー |

## 2. レコードトリガーフローの設計

- **保存前（高速項目更新）**: 同じレコードの項目を更新するだけなら最速。**他のレコードは触れない**。
- **保存後（アクションと関連レコード）**: 関連レコードの作成・更新、メール送信、他のフロー呼び出しなど。
- **非同期パス**: 外部連携など、時間がかかる処理を後で実行。
- **スケジュール済みパス**: 「完了予定日の 3 日前」のように、レコードの日付を基準に後で実行。
- **エントリ条件**と「条件を満たすように更新されたときのみ」の設定で、無駄な実行を減らす。

## 3. Flow の主な要素

- **データ**: レコードを取得・作成・更新・削除
- **ロジック**: 決定（分岐）・ループ・割り当て
- **画面**: 画面フローでの入力・表示
- **アクション**: メール送信、Chatter 投稿、承認申請、Apex 呼び出しなど
- ベストプラクティス: **ループの中で「レコードを取得／更新」しない**（ガバナ制限）。コレクションにためてループの外で一括更新する。
- **デバッグ**機能と**フローのバージョン管理**（有効なバージョンは 1 つ）。
- 失敗時の**障害パス**でエラー処理を書ける。

## 4. 承認プロセス

- レコードを承認者に回して**承認／却下**させる仕組み。
- 構成: エントリ条件 → 申請時のアクション（**レコードのロック**など）→ 承認ステップ → 最終承認／最終却下時のアクション。
- 承認者: ユーザー、キュー、**関連ユーザー項目（上司など）**。
- 複数ステップ・並行承認（全員承認／最初の 1 人）にできる。
- 申請は手動（ボタン）または Flow から自動で行える。

## 5. どの自動化を選ぶか

| 要件 | 選択 |
|---|---|
| 同じレコードの項目を保存時に設定 | レコードトリガーフロー（保存前） |
| 関連レコードを作る・メールを送る | レコードトリガーフロー（保存後） |
| ユーザーに入力させながら進める | 画面フロー |
| 定期的にまとめて処理 | スケジュールトリガーフロー |
| 上長の承認が必要 | 承認プロセス |
| 不正な値の保存を止めたい | 入力規則（自動化ではない） |
| 複雑すぎて Flow では難しい | Apex（開発者に依頼） |
