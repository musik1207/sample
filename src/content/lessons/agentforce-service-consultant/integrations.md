## この範囲で問われること

- サービスでよくある連携の要件
- 連携の方式（データのコピーか、参照か）
- テレフォニー・外部データ・バックオフィスとの連携
- 連携の設計で注意すること

## 1. よくある連携

| 連携先 | 目的 |
|---|---|
| 注文・EC システム | 注文状況・配送状況を見る、返品を受け付ける |
| 請求・ERP | 請求内容や支払状況を確認する |
| 電話（テレフォニー） | 着信時に顧客情報を表示、通話記録を残す |
| 製品・IoT | 機器の状態を見て、問題を予防的に検知する |
| フィールドサービス | 訪問作業の手配 |

## 2. 連携の方式

| 方式 | 特徴 | 例 |
|---|---|---|
| **データを参照するだけ（コピーしない）** | 常に最新。容量を使わない | **Salesforce Connect**（外部オブジェクト） |
| **データをコピーする** | レポートや自動化に使える。同期の管理が必要 | API による一括連携、ETL、MuleSoft |
| **画面で呼び出す** | 必要なときだけ外部の情報を取得 | Flow の HTTP コールアウト、外部サービス、Apex |
| **イベントで通知** | 変化をリアルタイムに伝える | プラットフォームイベント、変更データキャプチャ |

- 「エージェントが**見るだけ**で、データが大量・頻繁に変わる」→ Salesforce Connect が有力。
- 「レポートや自動化で使いたい」→ データをコピー。

## 3. テレフォニー

- **Service Cloud Voice**: Amazon Connect などと統合した電話機能。
- **Open CTI**: 既存の CTI ベンダーのソフトフォンを Salesforce に組み込む。

## 4. 設計の注意点

- **マスターはどこか**（どのシステムが正しいデータを持つか）を決める。
- **API の上限**や性能、エラー時の再試行と通知。
- **認証情報**は指定ログイン情報（Named Credential）で安全に管理。
- 連携のロジックが多いなら **MuleSoft** などの連携基盤を検討。
- AI エージェントのアクションとして外部データを呼び出す場合も、**権限とエラー時の応答**を設計する。
